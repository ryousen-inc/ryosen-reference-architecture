# 実装プロファイル

稜線リファレンスアーキテクチャ v0.3-draft / 追加章
最終更新: 2026-08-30

本章は、公開している[5つの設計原則](https://ryousen.co.jp/architecture/)と[三層のガバナンス](https://ryousen.co.jp/architecture/)に従属する。原則と矛盾する構成は、本章のどのプロファイルにも該当しない。

---

## 1. なぜプロファイルを分けるか

四層構成（記録・接続層／データ層／知能層／提示・運用層）に挙げた構成要素は、すべての案件に必要なわけではない。とくにデータ層には、RDFストア、PostgreSQL＋pgvector、オブジェクトストレージが並んでいる。これを全部立てた構成を既定として配ると、次の二つが起きる。

- **顧客側**: 運用できない規模のスタックが現場に残り、数年で誰も触れなくなる
- **実装側**: 見積りが膨らみ、本来やるべき語彙の作り込みに予算が回らない

設計原則5「地域で回せる軽さ」に、正面から反する。

一方で、後から層を足せない作り方をすると、二年目以降に積み上がるはずの観測が捨てられる。

プロファイルは、この二つを同時に避けるための取り決めである。**構成は案件に合わせて削ってよい。ただしデータの持ち方は削らない。** 削ってよいものと削ってはならないものを、あらかじめ分けておく。

## 2. 三つのプロファイル

### 概要

| | minimal（最小） | standard（標準） | full（完全） |
|---|---|---|---|
| データ層 | PostgreSQL（pgvector＋日本語全文検索） | ＋ オブジェクトストレージ、時系列テーブル、PROV-O射影バッチ | ＋ RDFストア（Fuseki）、SHACL検証、SPARQL照会 |
| 設置場所 | 顧客サイト | 顧客サイト | **原則、稜線側** |
| サーバ目安 | VPS 4GB / 4Core / SSD 200GB | VPS 8GB / 6Core / SSD 400GB ＋ 外部オブジェクトストレージ | VPS 16GB以上 |
| 月額目安 | 3,500〜4,000円 | 7,000〜8,000円＋ストレージ従量 | 12,000円〜 |
| 保守目安 | 月1〜2万円 | 月3〜5万円 | 稜線負担 |
| 運用主体 | 地域のIT会社 | 地域のIT会社 | 稜線 |

**金額の範囲について。** 上表の保守は、三者体制における**地域のIT会社側の見積り想定**であり、インフラ実費と合わせたものである。稜線の設計フィー（Step 0〜3）は含まない。初期実装費は案件の語彙設計の分量に左右され、構成だけでは決まらないため、本表には載せない。Step 1 アセスメントの報告時に、地域のIT会社から個別に概算を提示する。稜線の料金は[サービスのページ](https://ryousen.co.jp/service/)に掲載しており、本文書では重複して記載しない。サーバ価格は2026年8月時点のさくらのVPS（石狩リージョン、税込）を目安とした。

### minimal — 最小

**適用条件**（すべて満たす場合）

- 観測がテキストと数値に収まる（音声・動画を継続的に蓄積しない）
- 生メディアの総量が10GB未満
- 語彙を一社内で閉じて使う
- 抽出型が主で、検証サイクルが単年度以内または逐次

**構成**

```
[アプリ] ─ [PostgreSQL 16+]
             ├ pgvector（意味検索）
             └ PGroonga または pg_bigm（日本語全文検索）
[Caddy/nginx] + Let's Encrypt
日次バックアップ → 別サービス（必須）
```

RDFストアは置かない。オブジェクトストレージも立てず、画像・PDFはローカルディスクに置いてバックアップで守る。

**できること**: 検索、対象ごとの時系列カード、人手による転記修正、日次の業務導線
**できないこと**: 複数案件横断の照会、オントロジーに基づく推論、整合性の機械検証

**サイジング根拠**: レコード10万件・埋め込み10万チャンク（1536次元で約600MB）までは、4GBでインデックスがメモリに載る。同時利用者10名程度まで。埋め込み生成とAI転記は外部APIに投げるためCPU負荷はスパイクしない。ローカルで埋め込みモデルを回す設計にすると前提が崩れるので、この規模では選ばない。

### standard — 標準

**適用条件**（いずれかに該当）

- 音声・動画・写真を観測の一次資料として継続的に蓄積する
- 生成型を含む。結果が返る仕組みを先に作る必要があり、複数年にまたがって由来を追う
- 時系列の計測値と語りを突き合わせる

生成型の案件は、性質上ここから始まることが多い。答え合わせが自社の外で終わる判断を扱う以上、いつ・何を試して・どうだったかの連鎖を保存できなければ、そもそも仕組みが成立しないためである。

**構成**

minimal に加えて、

```
生メディア → 外部オブジェクトストレージ（S3互換）
             VPSにはハッシュ・URI・時間範囲のみを保持
PROV-O射影バッチ（SQL → Turtle、日次または任意実行）
時系列テーブル（PostgreSQL、必要なら TimescaleDB）
```

生メディアをVPS内に置かないことが要点。8GBプランのSSD 400GBでは、数年分の音声・動画に足りない。自前でオブジェクトストレージを立てる選択肢もあるが、顧客サイトでは運用対象が一つ増えるだけなので、マネージドを既定とする。

射影バッチは、この段階では**出力するだけ**でよい。Turtleを生成して稜線側に渡し、照会は稜線側の full で行う。顧客サイトにRDFストアを置く必要はない。

### full — 完全

**適用条件**

- 複数事業者・複数年の観測を横断して照会する
- 稜線オントロジー（`https://ryousen.co.jp/ns/ryosen#`）に基づく推論、SHACLによる整合検証を行う
- 語彙の突き合わせ（同じ現象に別の言葉が付いている状態の発見）を行う

**構成**

standard に加えて、Apache Jena Fuseki（TDB2、ヒープ4〜8GB）、SHACL検証、SPARQLエンドポイント。

**このプロファイルは原則として稜線側に置く。** 顧客サイトに置かない理由は三つある。

1. JVMの運用を顧客・地域のIT会社に負わせない（設計原則5に反する）
2. 横断照会は、そもそも一社のデータだけでは成立しない
3. 顧客の資産はデータであってRDFストアではない。設計原則3のとおり、顧客サイトからは常にRDB＋Turtle出力の形で全量を返却できる

顧客が full を自社に持つことを希望した場合は構成を渡すが、運用要員の確保を前提条件とする。

## 3. 共通不変条件

**プロファイルによらず、すべての実装が満たすこと。** 構成を削ってよいのは、この六条を守っている場合に限る。これを欠いた実装は、後から上位プロファイルへ上げられない。

1. **原本の同一性**
   すべての一次資料（スキャン画像、音声、写真、計測ログ）に、不変ID・暗号学的ハッシュ（SHA-256）・取得日時を持たせる。ファイル名や配置に依存しない。

2. **派生物の由来**
   転記テキスト、要約、抽出結果などの派生物は、必ず「どの原本のどの範囲から」「誰が／何が生成したか」「いつ」を列として持つ。PROV-Oの `wasDerivedFrom` / `wasAttributedTo` / `wasGeneratedBy` に一対一で射影できる形にする。AI生成と人手修正は必ず区別する。

3. **現象と帰属の分離**
   観測された事象と、語り手による因果説明は、別のテーブルに置く。熟練者の語る機序と実際の機序は異なりうる。両者を同じ列に混ぜた時点で、後から分離できない。

4. **語彙の非正規化保存**
   本人の言葉をそのまま保存する列と、正規化語を入れる列を分ける。正規化語で上書きしない。決まり文句でも一般的な説明でもない、体験そのものの言葉は、既存語彙に丸めた瞬間に価値を失う。

5. **追記のみ**
   修正は上書きせず、版として追記する。旧版は残す（`wasRevisionOf`）。誰がいつ直したかを含む。

6. **第3層を自動化しない**
   三層のガバナンスに従う。第1層（自動で知らせる）と第2層（助言する）までを自動化の範囲とし、第3層（人が決める）は自動化しない。プロファイルによらず適用される。

稜線は、この六条に対応するスキーマ定義とSQL→Turtle射影規則を提供する。実装は地域のIT会社が行う。**標準は稜線、実装は地域**という分担の実体は、この六条である。

## 4. 上位への移行

| 移行 | 引き金 | 作業 |
|---|---|---|
| minimal → standard | 音声・動画の蓄積開始、生成型への展開、複数年検証の必要 | オブジェクトストレージ接続、射影バッチ追加、VPSスケールアップ |
| standard → full | 横断照会・推論の必要 | 稜線側でTurtleを取り込む（顧客サイトの変更なし） |

さくらのVPSはスケールアップのみ可能でスケールダウンできない。上位プランを先に取らないこと。

standard → full は、共通不変条件を守っていれば顧客サイトに変更が生じない。これが六条を課す実利上の理由である。

## 5. サービスの段階との対応

| 段階 | プロファイルに関して行うこと |
|---|---|
| Step 0 体感セミナー | 判定しない。三類型のどれに当たるかまで |
| Step 1 アセスメント | **プロファイルの判定と根拠を報告書に含める。** 地域のIT会社の概算見積りもここで揃える |
| Step 2 設計・コア構築 | 共通不変条件に沿ったスキーマ設計、アクセス制御と個人情報の取り扱い設計、実装のハンドオフ |
| Step 3 稜線顧問 | 遅い輪（月次の問い見直し）の中で、プロファイルが実態に合っているかを点検する |

個人情報や社外秘を含む観測を扱う場合、紙で保管されていたものが検索可能になる時点で、漏えい時の影響が大きく変わる。誰がどこまで参照できるかの設計は Step 2 に含める。プロファイルの選択とは独立に必要となる。

---

## 6. プロファイルを選ぶ順序

規模から選ばない。次の順で決める。

1. **何を観測するか**（テキストか、生メディアを含むか）
2. **抽出型か生成型か**（結果が返る仕組みを先に作る必要があるか）
3. **語彙を誰と共有するか**（一社内か、横断か）
4. 最後に、データ量とサーバ

1〜3で minimal に収まる案件を、データ量を理由に standard にしない。逆に、量が小さくても複数年の由来追跡が要る案件は standard から始める。**判断基準は容量ではなく、観測の設計である。**

---

## 7. 選んではならない構成

- 顧客サイトにRDFストアを置き、保守を顧客に委ねる
- 共通不変条件を省いて実装費を削る（移行不能になる。削るなら構成を削る）
- 生メディアをVPSのローカルディスクに蓄積し続ける
- 語彙を正規化して上書き保存する
- 判断の自動化（第3層）を含む提案
